# ADR-0001: System boundary
Status: Accepted
## Context
We need prospective authorization with prospective safety, deterministic evidence and explicit authority.
## Viable alternatives
- post-hoc audit
- external approval
## Decision
Use typed inline middleware and single-use grants.
## Tradeoffs
latency for explicit authority.
## Consequences
This boundary participates in the grant decision and fails closed. Downstream contexts receive typed results rather than ambiguous flags.
## Validation
Validate with release only after policy, risk and evidence, bound to the exact candidate commit.


## Detailed rationale
The control plane sits between a planning agent and any privileged executor. We rejected post-hoc audit because it can explain damage but cannot prevent it, and rejected human approval as the only control because long action chains create review fatigue. The boundary accepts a complete ActionBatch and returns either no grant or a nonce-bound grant scoped to the exact evidence digest.

## Executed boundary and proof
The system boundary decision is implemented as a typed boundary, not a documentation-only convention. cs-orchestrator, cs-verifier, and cs-executor-gate; the public end-to-end test proves no release when any assurance is removed.

## Review trigger
Revisit this decision if its upstream API, trust boundary, workload distribution, or failure semantics change. A revision must preserve fail-closed authorization, deterministic replay, and an ablation that demonstrates what capability the decision contributes.
