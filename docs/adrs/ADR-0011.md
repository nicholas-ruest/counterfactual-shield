# ADR-0011: Ledger
Status: Accepted
## Context
We need audit ownership with prospective safety, deterministic evidence and explicit authority.
## Viable alternatives
- mutable DB
- logs
## Decision
Use append-only hash-linked records.
## Tradeoffs
checkpoint compaction.
## Consequences
This boundary participates in the grant decision and fails closed. Downstream contexts receive typed results rather than ambiguous flags.
## Validation
Validate with corruption reject, bound to the exact candidate commit.


## Detailed rationale
Every decision record carries a monotonic sequence, previous record hash, current record hash, decision, batch ID, and RVF seal. A mutable database row was rejected because updates erase decision history. The ledger recomputes every link after append; persistence beyond this reference implementation remains an explicit limitation.

## Executed boundary and proof
The ledger decision is implemented as a typed boundary, not a documentation-only convention. cs-ledger chain verification and orchestrator post-append verification.

## Review trigger
Revisit this decision if its upstream API, trust boundary, workload distribution, or failure semantics change. A revision must preserve fail-closed authorization, deterministic replay, and an ablation that demonstrates what capability the decision contributes.
