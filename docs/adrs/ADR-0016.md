# ADR-0016: API
Status: Accepted
## Context
We need stable contract with prospective safety, deterministic evidence and explicit authority.
## Viable alternatives
- direct crates
- REST daemon
## Decision
Use typed service facade.
## Tradeoffs
no network v1.
## Consequences
This boundary participates in the grant decision and fails closed. Downstream contexts receive typed results rather than ambiguous flags.
## Validation
Validate with vertical slice, bound to the exact candidate commit.


## Detailed rationale
ShieldService is the application facade: construction validates configuration, example executes the full workload, and evaluate returns combined/baseline/ablation reports. Exposing every adapter directly was rejected because callers could bypass the verifier or issue grants from partial receipts. The facade owns no mutable global state.

## Executed boundary and proof
The api decision is implemented as a typed boundary, not a documentation-only convention. cs-api facade unit test and crates/cs-api/tests/end_to_end.rs.

## Review trigger
Revisit this decision if its upstream API, trust boundary, workload distribution, or failure semantics change. A revision must preserve fail-closed authorization, deterministic replay, and an ablation that demonstrates what capability the decision contributes.
