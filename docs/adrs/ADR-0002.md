# ADR-0002: Action batch
Status: Accepted
## Context
We need intent and order with prospective safety, deterministic evidence and explicit authority.
## Viable alternatives
- flat events
- opaque transcript
## Decision
Use validated action DAG.
## Tradeoffs
early rejection.
## Consequences
This boundary participates in the grant decision and fails closed. Downstream contexts receive typed results rather than ambiguous flags.
## Validation
Validate with cycles, duplicates and missing parents, bound to the exact candidate commit.


## Detailed rationale
ActionIntent dependencies are part of the authorization subject, not presentation metadata. A batch is rejected when empty, when an identifier is duplicated, when a dependency points outside the batch, or when depth-first traversal detects a cycle. Per-action requests alone were rejected because their local permits cannot express chain-level escalation.

## Executed boundary and proof
The action batch decision is implemented as a typed boundary, not a documentation-only convention. cs-action cycle and reference tests plus the three-step frozen workload.

## Review trigger
Revisit this decision if its upstream API, trust boundary, workload distribution, or failure semantics change. A revision must preserve fail-closed authorization, deterministic replay, and an ablation that demonstrates what capability the decision contributes.
